# Sources

A **source** is one store's client on this machine: Steam, Epic, GOG, EA, Ubisoft and Battle.net; Xbox next (M4). The games added by hand are a source too, the library's own (below). Each store is a crate `source-<store>` behind one interface, `model::Source` (`crates/model/src/source.rs`), and the library merges them all into one.

## The interface

```rust
pub trait Source: Send + Sync {
    fn key(&self) -> &'static str;                         // "steam": games.source, never changed once released
    fn name(&self) -> &'static str;                        // "Steam": the log and the screens
    fn read(&self) -> anyhow::Result<Option<Found>>;       // the games; Ok(None): client not installed
    fn start(&self, game: &Game) -> Option<Start>;         // how to start one
    fn ask(&self, game: &Game, ask: Ask) -> Option<Start>;  // what installs or uninstalls one
    fn running(&self, game: &Game) -> bool { false }       // the store's own word that it runs
    fn installs(&self) -> Option<Vec<Install>> { None }    // its installs under way: the Queue
    fn installed_now(&self) -> Option<Vec<String>> { None } // its cheap word of what is installed: changes in its client
    fn uninstalls_by_itself(&self) -> bool { false }       // asking is all an uninstall takes
    fn installer(&self) -> Option<&dyn Installer> { None } // its own way to install and steer installs
}

pub struct Found { pub library: Library, pub from: String }
pub enum Start { Address(String), Program { path: PathBuf, args: Vec<String>, dir: Option<PathBuf> } }
pub enum Ask { Install, Uninstall }
```

- **`read`** lists every game the client's own files say the user has, installed or not. Each `Game` has `source` set to the key and `source_id` to the store's own id for it (Steam's appid, `"440"`), its install state (`installed`, `install_dir`, `size_on_disk`), its art (`cover`, `hero`, `header`, `square`: paths to what the client has cached on disk, so finding art is part of reading; and `online`, what the client's files say of the store's art online, "Art" below), its play history where the client keeps one (`last_played`, `playtime_minutes`) and what the store says of it (`developers`, `released`, ...). `Library::user` is the signed-in user's name where the store has one; `Library::collections` the store's own groupings, `None` when they could not be read. `Found::from` is where it was read from, for the log line `<key>: <n> games from <from> in <ms> ms`.
  - **Client not installed:** `Ok(None)`. Nothing is logged and the source's games stay in the database as they were.
  - **Installed but unreadable:** an error, with the place in its context. The library logs `<key>: <error>`, passes over the source, and loads the rest; the source's games stay as they were.
  - It runs off the UI thread, at start (after the first frame when the database has games). Keep it to the client's local files: no network, no sign-in.
- **`start`** gives an address the client takes (`steam://rungameid/440`, a protocol URL, `shell:AppsFolder\<AUMID>`) or a program to run with its arguments and folder (a game added by hand, a GOG game's own exe, `Battle.net.exe --exec=...`). The shell opens it, shows the Launch screen and follows the game by its windows: those of programs under `Game::install_dir`, so a game with no install folder can't be launched.
- **`ask`** gives what asks the client to install or uninstall the game, opened as `start`'s is: Steam's `steam://install/<appid>`, a client's command line (GOG's `GalaxyClient.exe /command=installGame`), a game's own uninstaller (`unins000.exe`); `None` when there is nothing to ask. The Tile menu and the Game hub offer Install and Uninstall for any game that has a source.
- **`running`** is looked at a few times a second while a game runs, alongside its windows: Steam's is its registry's `Apps\<appid>\Running`. A store with nothing like it keeps the default.
- **`installs`** says what the client has under way, from its local files: each game being installed by its `source_id`, `Queued` (waiting its turn), `Downloading { done, total }` in bytes, or `Paused { done, total }`; an update of a game already installed is not one. `Some(vec![])` is nothing under way; `None` (the default) means the store keeps no word of its installs that can be read, and its games never join the Queue: Install opens its client, whose own window shows how it goes. It is asked once a second, off the UI thread, while the Queue holds something or an install was just asked for, and every five seconds otherwise (`library::queue::WATCH_EVERY`), so that an install started in the store's own client while the Dashboard runs joins the Queue (#171): keep it to a few small files. A game it reports joins the Queue even when the install was started in the client; once it no longer reports it, the source is read again, and the game leaves the Queue installed or dropped by what `read` then says. Only Steam has one (`appmanifest_<appid>.acf`'s `StateFlags` and bytes, and the registry's `Apps\<appid>\Updating` for the download that is running; the manifest's bytes are written only now and then, at 0%, 11% and 100% of one real download, so the running download's are counted live as the Bundle's `DownloadedSoFar` counts them: what Steam's own `steam.exe` has written since the download was first seen, on top of what the manifest had staged then, scaled from staged to downloaded bytes by the manifest's two totals, never below the manifest's own count; with no Steam process to ask, the manifest's; and until the writes first move, no whole, which the screens show as "Installing..." with no share; `--log-queue-sources` prints that count beside every other candidate once a second, `source_steam::probe`). Where the user has Steam's CEF debugger on and Steam runs, Steam's own download overview (`source_steam::overview`, its Downloads page's) goes first: its speed is Steam's (`Install::speed`, shown in place of the Queue's own), and its bytes where it names them plainly; which of its `progress` entries is which is not yet known. A game whose manifest says installed is not done while Steam is still at it (`source_steam::follow`, #132): Ricochet's said so ten seconds before Steam had fetched the Half-Life content it needs. It stays installing while the overview names it, while the registry's `Updating` says so, or, without the overview, while another app that turned up under way within 30 seconds of it is under way (reasoned: taken as content it needs); the research found no honest local signal of an install in progress for the others (docs/research/stores.md).

- **`installed_now`** (#171) is the store's own cheap word of which games are installed now, from the same small files as `installs` (Steam's app manifests, `StateFlags` as `read` takes them): the Queue's thread looks at it every five seconds and reads the source again when it changes, so a game installed or uninstalled in the store's own client reads so without a restart (`queue: steam's installed games changed in its own client (12 then, 11 now): reading it again`). None, the default: only a read finds such a change.

- **`installer`** (#170) is the store's own way to install, uninstall and steer an install under way, the one seam every store's install plugs into (docs/research/installs.md, 10.1). None, the default: the store is asked by `ask`, and its installs cannot be paused or cancelled from here. "Installs" below.

- **`uninstalls_by_itself`** says whether asking the store to uninstall (`ask`) is all it takes (Steam's `+app_uninstall`, which asks the user nothing): the Queue's thread then says in the log when the game is still there two minutes on. Any other store's uninstall is the user's to finish in a window of its own (Settings' installed apps, a game's uninstaller): it is followed for ten minutes, as the Bundle's `AskedUninstallGivesUpAfter`, and the wait then ends quietly. An Uninstalled Toast shows only once the game has really gone, either way.

## Installs

```rust
pub trait Installer: Send + Sync {
    fn can(&self) -> Can;                       // pause (and resume), cancel, choose a folder, uninstall quietly
    fn folders(&self) -> Vec<Folder> { .. }     // where it may install: path, free bytes, the default
    fn install(&self, game: &Game, folder: Option<&Folder>, open: &mut dyn Opener) -> Result<(), Refusal>;
    fn uninstall(&self, game: &Game, open: &mut dyn Opener) -> Result<(), Refusal>;
    fn steer(&self, game: &Game, steer: Steer, open: &mut dyn Opener) -> Result<(), Refusal>; // Pause, Resume, Cancel
}
pub enum Refusal { Unsupported, Failed(String) }
```

`model::installer`. Every method but `can` defaults to `Refusal::Unsupported`, so a store builds only what its route can do, and `can` says the same: the Queue's menu rows follow it (docs/spec/manage-queue.md, section 8), each hidden where its store cannot. Each call returns once the store has been asked; what then happens is read from `installs`, which stays the one place progress comes from, whatever route started the install. An installer acts through an `Opener` (`shell::store::Addresses`: opens an address, runs a program), so a test sees what it asked and nothing runs; a route that needs no program (a client's local API, a helper's process) acts itself. Calls are made on the window's thread, as `ask`'s opening always was: one that may block (a call over Steam's CEF debugger waits up to 25 s for its answer) goes to a thread of its own, and where it falls back to the store's way later, opens that with the opener's `detached()` copy, which a thread may keep (the window's openers give one; an opener with none has the store's way taken at once).

- **Install and Uninstall** (`shell::store::ask`) go through the game's store's installer where it has one, and fall back to `ask` where it answers `Unsupported`, as for a store with none. An install goes into the folder chosen: the answer to "Where do you want to install X?", asked where the store has more than one folder and `Can::choose_folder`, else the store's default as Settings > Storage keeps it (`storage.default.<store>`), else the installer's own (`installer::default_folder`) (docs/spec/storage.md; #179). Before either, where the library has the same game, not installed, from other launchers whose stores can install it (`Source::can_install`: an installer, or something `ask` gives), "Install from" asks which launcher (docs/spec/install-from.md; #249).
- **Pause, Resume and Cancel** (`shell::store::steer`, `Effect::Steer`) only through an installer; a store without one, or one that cannot, is said so in the log (`store: Steam can't pause <game>'s install from here`). Pause covers resume. Cancel deletes what was fetched: the game leaves the Queue dropped.
- **Steam's** (#171): Steam's own client calls over its CEF debugger where the user has it on (`source_steam::client`, "Steam's own calls" below), else today's route (its console over CEF, else `steam.exe -silent`). Through the client: install into a library of `folders()` (Steam's libraries from `libraryfolders.vdf`, by their roots; the default asks the client for the one it marks default), pause, resume, cancel, and uninstall with no prompt. An install or uninstall the client does not take falls back to `steam.exe` as before; pause, resume and cancel have no fallback (`steam.exe` has no word for them) and are offered only while the debugger is on (`Can`). With the debugger off: Steam's default library only, no Pause, Resume or Cancel.
- **Installed, extras still coming in** (`InstallState::Extras`, #188). A game whose own files are in while its store fetches more for it (Steam's subscribed Workshop items) is installed: Play is offered, its tiles read it installed, and the Ready to play Toast fires then (the user's decision on #188); its row stays in the Queue, reading **Downloading Workshop content** with the items in of those subscribed to, their bytes where the record gives a size for every item, the share by the bytes else by the items, and never a speed. It leaves with nothing more said when the store is done. Steam's is read from `steamapps/workshop/appworkshop_<appid>.acf` and the folders in `steamapps/workshop/content/<appid>` (`source_steam::installs::workshop`); an app whose record says `NeedsDownload` is held installing with no download overview at all (`source_steam::follow`).

### Battle.net through its Agent (#172)

Blizzard's `Agent.exe`, the client's own downloader, answers HTTP on 127.0.0.1 (`source_battlenet::agent`). Nothing of Blizzard's documents it: what is relied on was read in other people's tools and in the TV PC's first try (2026-11-18, Agent 2.42.1.9886: docs/research/installs.md, section 7, with their commits), and every guess is in one file, `source_battlenet::agent::calls`.

**Which Agent is asked.** The one on the port `Agent.dat` names, else on a port an `Agent.exe` of that folder listens on, else 1120, where one gives a token. On the TV PC the client's own Agent (started by Battle.net with `--session=...`) listened on `Agent.dat`'s port and answered `GET /agent` with 401 and no body, with or without the phoenix user agent. Such an Agent is asked once more with its process id in a `pid` header (redact7's way); if it still gives no token, **no Agent is started beside it**, nor while `Battle.net.exe` runs: two Agents would both write `product.db` and the client can take an install over (barncastle's own warning), and DroidDeck, the one tool that thought of it, waits for Battle.net to close before it starts its own (barncastle, HSCentric and redact7 start one, or use one, regardless). The client is opened on the game instead, said with why: `battlenet: agent: an Agent the Dashboard did not start answers on port 61921 and gives it no token (port 61921 (Agent.dat): 401, no token; port 61921 with pid 4242: 401, no token): Battle.net's own; no second Agent is started beside it`. So the Agent's route is for a PC where Battle.net is closed (exited, not in the tray). There the Dashboard starts the Agent itself, takes its port from its own process (as barncastle and HSCentric do), and **stops it** once nothing of the Dashboard's uses it (the install done, abandoned or cancelled, the uninstall seen done): `DELETE /agent`, then killed if it has not gone 5 s on (`agent: the Agent the Dashboard started (pid <n>, port <n>) stopped: it exited <n> ms after DELETE /agent`). On Windows it is in a job object that kills it when the Dashboard's process ends, however it ends. An Agent the Dashboard did not start is never stopped.

**Stopping before the download.** With `DASHBOARD_BATTLENET_NO_DOWNLOAD=1` an install fills in the form unfinalized, logs what the Agent made of it (`battlenet: lbra: the form filled in: locales ...; its folder "..."; 580000000 bytes; size state 1009; not finalized`), abandons it (`the install abandoned (stopped before the download ...): DELETE /install/libra -> ...`) and leaves the Queue with nothing downloaded and the client not asked. There is no known point after the form is finalized and before bytes move: DroidDeck and redact7 send nothing after the finalized post, so it is taken to start the download.

**Every call is one line of the log**, its token never (written `<token>`), nor the session or the user's names (`<masked>`): `battlenet: agent: install lbra: POST /install {...} -> 201 {...}`. Then `the Agent took the install` and `its progress read on /update/libra, /install/libra, the game on /game/libra`. The progress is asked silently once a second; each path's first answer is logged whole (`battlenet: lbra: /install/libra: first answer: 404 {}`), and any change of its status (`/update/libra now answers 200 {...}`), `progress read on /update/libra` when the path read changes, and `battlenet: lbra: downloading, <n> of <m> bytes, <r> bytes a second; /update/libra said {...}` when the state changes and each tenth of the way, the answer read whole, so that one real run shows how the Agent's answers read. Then `done: product.db says installed`, `uninstalled: product.db no longer says installed`, `<verb>: the Agent took it`.

**When an install the Agent took is over** (`source_battlenet::installing`), and only then: `product.db` says installed (done; looked at each second once an answer says the download is done, every ten seconds before); the Agent names an `error` above 0 on a 2xx answer, or on a path that has answered 2xx (failed); the user cancels; or every progress path **and** the game's have said nothing (no answer, or an answer that says nothing, such as `404 {}`) for 60 s with the Agent's process gone, or for 15 minutes with it there. **A 404 on one path is never by itself the end**: the TV PC's first real install was taken for stopped on `/install/libra`'s 404, and the Agent the Dashboard had started, and its download, were killed. While it is under way the follower holds the session, and with it the Agent the Dashboard started, which is stopped only once the install is over. If Battle.net's own client starts meanwhile, the Dashboard's Agent is left running, said once: `battlenet: lbra: Battle.net.exe (pid ...) started while the Agent the Dashboard started downloads it: that Agent is left running until the install is over ...` (the client may take the install over, barncastle's warning; `product.db` then says when it is done). An install that stops by itself is **told with why**, in the Queue's stopped row and its Toast (`Stop::Failed`: "Couldn't install"), and the log: `battlenet: lbra: stopped: the Agent names error 2421: ... on /update/libra ({...}): told "Battle.net's Agent stopped it with error 2421: the PC does not meet its needs, or there is not enough space."`, or `stopped: its Agent stopped answering: ...: told "Battle.net's Agent stopped answering. Install it again, or finish it in Battle.net."`.

**When the Dashboard ends mid-download.** The Agent the Dashboard started is in a job object that kills it with the Dashboard's process, however it ends (closed, crashed, killed), and its download with it: a game folder part-filled is left, and `product.db` has the product, not installed, at that folder. Nothing offers it in the Queue on the next start (Resume would need the Agent's word on a download it no longer has). Install on it again goes through the Agent as before, and **into that same folder** (`product.db`'s `install_path`, said in the log: `product.db has a download of it not finished in ...: installed again into that folder`), so that the Agent may pick up from the files there. That it does is not known for sure: barncastle's README says only that a folder that already holds the product is updated, and barncastle tells the user to "Launch the Battle.Net app to resume installation" when another program takes its install over; the form may instead answer `game_dir` 800 (the folder holds a game), in which case the Agent's refusal opens the client on the game, which shows the download and resumes it itself. **Where the Agent does not answer or refuses**, today's route, said with why: `battlenet: lbra: the Agent did not take the install (error 2221: ...): asking Battle.net instead: ...Battle.net.exe --game=libra`, and an uninstall the game's `UninstallString`. An install the Agent forgets, or that errs, leaves the Queue dropped.

**Which games can be installed.** Nothing on the PC says which games the account owns: `Battle.net.config` names those installed or played, `CachedData.db` and the client's `Cache` only fragments (docs/research/installs.md, section 7). So the games not installed are a table built in (`source_battlenet::catalogue`: product code, uid, launch code and name, after Lutris's and PlayniteExtensions' tables, Tony Hawk's Pro Skater 3 + 4 checked against Blizzard's public patch server), listed not installed while the client is installed. **Whether the account owns one is not known until the Agent answers its install**; one it does not is refused (2221) and opened in the client instead, where the user sees what Blizzard says.

**The stand-in** (`source_battlenet::standin`): the fake Battle.net's `Agent\Agent.9999\Agent.exe` is standin.exe, which serves these calls on a free port it writes in the fake's `Agent.dat`, answers the fake's `catalogue.json` (its owned products installable, the others 2221), answers `GET /agent` with a session and user names beside the token as the TV PC's did, gives the form as the TV PC's first answer had it (201; `language.error` 704 until a locale of its list is posted as the list writes it; a `dirname` of its own, the name with no spaces or apostrophes; `required_space_info.state` 1005 until the second post of the choices, then 1009; `warning` 806), starts the download only once the form is posted finalized, takes a form back on `DELETE /install/<uid>`, answers once finalized as the TV PC's Agent did (`GET /install/<uid>` 404 `{}`, the progress on `GET /update/<uid>` in the wiki's shape with three-part byte arrays, the game on `GET /game/<uid>`, `response_uri` and `result_uri` in the finalized post's and `POST /update`'s answers), counts out 48 MiB in eight steps `STANDIN_HELPER_STEP_MS` apart into the folder given, honours the guessed pause, resume and cancel on `/update/<uid>`, names an error on its progress where a test asks (`Served::fail`), writes the fake's `product.db`, `aggregate.json` and registry when an install ends or an uninstall is asked, and ends on `DELETE /agent`. It refuses a caller without the phoenix user agent or the token (401). Started with `--session=...`, as Battle.net starts its own, it answers 401 with no body to everything, as the TV PC's own Agent did. Its every request is a line in standin.log, secrets masked. The TV payload is `e2e/payloads/battlenet-agent`.

A source holds no state that changes, but for what Steam's keeps between looks at its installs (each download's live count and which apps are held as installing, behind a lock: `source_steam::follow`): one is made at start and shared, as `Arc<dyn Source>`, by the thread that reads the sources and the window that starts games.

## How the library merges them

`library::sources::read(&sources)` reads each in turn and logs what it gave; `Database::sync_all` merges each that was read under its key (`Database::sync`, per source). In the database a game is the row `(source, source_id)`:

- A game owned in two stores is **two games**, each with its own row, history and store mark.
- A game a source no longer lists (uninstalled, or no longer owned) is marked gone and not shown; it keeps its row, its Play sessions, favourite and hidden, and comes back as the same game if the source lists it again.
- Play sessions, favourite and hidden are the user's: a refresh never touches them. A source's own word on favourites or hidden is taken once, as the game is first seen.
- The snapshot's `user` is that of the source with the most games shown.
- A launcher switched off in Settings > Launchers (docs/spec/launchers.md) is not read, at start-up or by Update now, and its games are left out of the snapshot and every query (`launchers::shown`), their rows untouched. Each read notes what it found of each launcher and when (`launcher.<key>.found`, `launcher.<key>.read` in the settings table), which the page shows.

## Games added by hand

The source `manual` (`library::by_hand::Manual`, docs/spec/apps.md) is the user's: its games are added, renamed and removed in Settings' Games & apps, straight into the database (`Database::by_hand`), with `source_id` the program's full path. Its `read` gives nothing, so a sync never touches them; its `start` runs the program in its own folder. Apps are not games and not a source's: they are kept apart, in the `apps` table, and started as they are.

## Adding a source

1. A crate `crates/source-<store>` depending on `model` and `anyhow`, with a type that implements `model::Source`, its parsers tested on made-up fixtures only (never a real machine's files: `data/` is private).
2. One line in `crates/app/src/sources.rs` (`sources::all`), which is the list, in order, and one dependency in `crates/app/Cargo.toml`.
3. Its mark on tiles: a variant of `screens::home::Source` by its key, with the name the Game hub writes, and its mark in `screens::drawn` (docs/spec/home.md 3.3.1): the store's own logo as vector path data in `screens::path_data::marks` (the Bundle's where it has one, else Simple Icons', with the version), and a row for it in NOTICE.md naming its owner. Until it has one its games carry the plain box.

4. Its fake for the VM: a `fixture` module that writes a made-up install whose installed games are the stand-in (`crates/standin`, `standin make-<store> <dir>`), a flag naming a folder the source reads in place of the machine's own (`--steam`, `--epic`, `--gog`, `--ea`, `--ubisoft`, `--battlenet`, `--xbox`), and a function in `e2e/payloads/lib/E2E.psm1` that sets it up. A source that reads the registry reads it through `source_kit::registry::Registry`, which is Windows' or, for a fake and the tests, a `registry.json` of keys and values in the fake's folder.
5. For the tests on the TV PC (safe mode, `e2e/README.md`): the flag given an empty folder reads no games and never falls back to the machine's own, and the flag's name is in `$StoreFlags` in `E2E.psm1`, which starts the Dashboard on a fake or an empty folder for every store there. A store reached by an address (`steam://`, `com.epicgames.launcher://`, `uplay://`) has its stand-in in `standin open-address`, which finds the fake's folder in `handlers.json` beside it, never the registry; the helper that sets the fake up registers nothing in safe mode (`Register-Fake` in place of `Register-UrlHandler`).

Nothing in `library` or `shell` changes.

## The stores

Each from docs/research/stores.md, where the reasons are. What only a signed-in PC can confirm is listed under "Needs a human" in #14.

**Steam** (`source-steam`, key `steam`). Its install from `HKCU\Software\Valve\Steam\SteamPath`, or `--steam <root>` (an empty folder there is no Steam, and no games); the games, art and play history from its `appcache`, `steamapps` and `userdata` (the crate's own documentation says which file gives what). Starts through `steam://`. Installs and uninstalls as the Bundle does, by the first of its two routes that can be taken (`shell::steam`, #132). Where the user has Steam's CEF debugger on (an empty `.cef-enable-remote-debugging` in Steam's folder, Steam started again: the user's to do, never the Dashboard's, since any program on the PC can then drive Steam) and Steam is running, the command is typed into Steam's console from its windowless `SharedJSContext` page (`SteamClient.Console.ExecCommand('app_install <appid>')`, `source_steam::cef`), which raises no window. Otherwise `steam.exe -silent +app_install <appid>` and `-silent -console +app_uninstall <appid>` (its `steam.exe` from the registry's `SteamExe`, or in `--steam <root>`; `steam://install/<appid>` when there is none). A running Steam brings its main window up as it takes a command that way, whatever `-silent` says (seen on the real machine), so Steam's open windows are sent to the tray first, and a watch on Windows' own events (`SetWinEventHook`: a window of Steam's shown, given the foreground or renamed) hides Steam's main window the moment Windows tells of it and closes it to the tray, for fifteen seconds (45 when `steam.exe` starts Steam), the foreground locked for the first five while a running Steam takes the command. Every window of Steam's met is a `store:` line in the log, with its class, title, time and what was done to it. Only the window titled "Steam" is hidden: sign-in and Steam Guard are left to ask the user. A game reads installed only once its manifest's `StateFlags` say fully installed; `installs` reads the others. Whether it reads installed takes 4 `FullyInstalled`, 2048 `Uninstalling` and 64 `SharedOnly` (the update bits 256, 512 and 1024 say only whether an install is under way); any other bit is ignored, as the Bundle's `IsInstalled` ignores it. A manifest with 64 is content Steam fetched only to share with another app: Steam's content log says `Fully Installed,Shared Only` for 68 (on the TV PC, 2026-11-17, app 70, Half-Life, fetched for another game, #171). It reads neither installed nor an install under way (`installs::SHARED_ONLY`), so it is not in the library's installed games, the Queue's rows or counts, or Recently installed. A departure from the Bundle, which ignores 64 and shows it installed. Unverified: whether the manifest has 64 while such content downloads; if not, it shows queued until it is done, and then drops out of the Queue rather than reaching Recently installed. A manifest Steam leaves at 514 (`UpdateRequired | UpdatePaused`, the files gone) after a cancel in mid-download reads neither: the game is offered Install, which works on it (flags 1026 on the TV PC). `running` is its registry's `Apps\<appid>\Running`.

**Epic Games** (`source-epic`, key `epic`, the game's `source_id` its `AppName`). Three launchers' records are read. A current launcher (seen on a real machine on 2026-11-16, build EpicInstaller-20.3.3) leaves its installs to Epic Online Services' install helper, one `.egi` record per installation in `%ProgramData%\Epic\EpicOnlineServicesShared\InstallHelper\InstalledItems` (only that folder: its sibling `EpicOnlineServices\InstallHelper` holds the launcher's own components, which are not games); a record is installed when its `state` is `Installed` and its `dir` is there, its size its `manifestData.buildSize`, and a record of a version other than `v4`, or broken, is passed over with a log line. The library itself: the eglv2 launcher's files first, `%LOCALAPPDATA%\com.epicgames.eglv2` (`installations.jsonl`, the library and catalogue caches; known from one project only, and absent on the real machine), and when they give no games the old launcher's: the installed games from `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests\*.item` (DLC and Unreal Engine content left out; a manifest whose folder has moved put right by `UnrealEngineLauncher\LauncherInstalled.dat`), and those owned and not installed from the catalogue cache `Data\Catalog\catcache.bin`, which exists only once the launcher has been signed in on the PC. The game's name, developer and art addresses come from the catalogue cache for every record. No art on disk (the launcher caches the pictures' addresses, not the pictures: those, its catalogue items' `keyImages`, are `Game::online`, which the art lookup downloads) and no play history (Epic keeps it on its servers). A game starts through the launcher's link, `com.epicgames.launcher://apps/<namespace>%3A<item>%3A<AppName>?action=launch&silent=true`, the launcher checking the game is the user's; Install asks with the same link and `action=install`, which shows the launcher's own dialog; nothing outside the launcher can uninstall, so Uninstall asks nothing. `running` is left to the game's windows. `--epic <dir>` reads `<dir>` as `%ProgramData%\Epic` (and `<dir>\com.epicgames.eglv2` as the eglv2 launcher's); the VM's fake is `standin make-epic` (one game installed by the install helper, one by a manifest, one owned with an install in progress, and the launcher's own components beside them), with `standin epic-url <dir>` registered for the launcher's links as the stand-in launcher. **Xbox** (`source-xbox`, key `xbox`, the `source_id` the package family name, which stays through updates). Installed games only, from the machine alone, with no sign-in: a game is a package registered for the user whose root has a `MicrosoftGame.config` (every GDK game has one, no app does; an older UWP game from the Store has none and is not listed: add it by hand). The packages are found two ways: the folders each drive's `.GamingRoot` names (each game's package in `<folder>\<game>\Content`) and `Program Files\ModifiableWindowsApps`, and the package manager's list of the user's packages (WinRT `PackageManager`, as Playnite reads it), which finds games still under `WindowsApps` and packages registered from anywhere; a game in a folder the package manager does not list for this user is passed over. The name is the config's `ShellVisuals` `DefaultDisplayName`, else the manifest's (an `ms-resource:` name looked up in the package's resources). `install_dir` is the package's root, where its programs are, so the shell follows the game's windows. Size on disk is 0: nothing gives it without walking the whole folder. Art from the package's own logos (the largest scale where the plain file is absent): the square its large tile logo (`Square480x480Logo`, else `Square310x310Logo`; the 150, the store logo and the 44 only for a game with no `StoreId`), no cover (a package has nothing portrait: "Art" below), the hero the config's `SplashScreenImage` (else the manifest's splash screen), the header the manifest's `Wide310x150Logo`. Start: `shell:AppsFolder\<family name>!<application id>`, the application the config's executable names, which Windows activates as the Start menu does (never the game's exe, which would skip its app-launch). The config's `StoreId` is also `Game::online.product`, by which the Store's own art is asked for. Install: `ms-windows-store://pdp/?ProductId=<StoreId>` where the config names its product. Uninstall: Settings' installed apps, `ms-settings:appsfeatures`, where the user removes it, as Playnite does: whether removing the package from outside removes a GDK game cleanly is not known. `running` is the store's own word here: a process of this session runs as the package's family (`GetPackageFamilyName`), which covers the hand-over from `GameLaunchHelper.exe` to the game. The Game Pass catalogue and the games owned and not installed are Xbox's servers' to say, with sign-in: nothing is read of them. `--xbox <dir>` reads `<dir>` as a drive (its `.GamingRoot` and the folders it names) and never the package manager, an empty folder having no games; the VM's fake is `standin make-xbox`, whose Tidewater Trials is a whole package that the VM test registers from its loose files.

## Art

Decided in #9, built in #80; square art and the stores' own art online in #110; any game at every store, in the user's order, in #246 (research: docs/research/art-sources.md). A game has four pictures: **cover** (portrait, 600x900), **hero** (wide background), **header** (landscape, 920x430) and **square** (1:1: what a square tile shows, Home's Recent row among them; docs/spec/home.md 3.3). One lookup in `library::art`, the same for every source's games and every kind, in this order:

1. **What the source gave**: the pictures its client keeps on disk, as `read` found them (`Game::cover`, `hero`, `header`, `square`). It always wins.
2. **Our own cache**, `art/<source>/<source_id>/{cover,hero,header,square}.{png,jpg,webp}` in the data folder (`ArtDir`; a key or id is its folder's name with every byte but letters, digits, `-` and `_` written `%XX`). `Database::snapshot` fills from it each picture a game's source did not give, so the screens never know where a picture came from.
3. **The game's own store online** where it is none of the four below (`Store::Own`): GOG's catalogue for a GOG game, and the picture addresses a client named (the Epic launcher's). No key.
4. **The online sources, in the user's order** (Settings > Art's **Art sources**, `art.order`, `model::ArtOrder`; docs/spec/settings.md 16.8). The default is Playnite's: **Steam's store**, **Xbox** (the Microsoft Store's catalogue), the **PlayStation Store** (`StoreArt`, below; no key, sending only a store's own id or the game's name), then **SteamGridDB** (only when the user has entered their own API key). Each can be moved and turned off. **Each kind of picture falls through them apart**: a Steam game whose square neither Steam nor SteamGridDB has gets Xbox's BoxArt, or PlayStation's square. A game that is not the store's own is found there **by its name** (below, "Matching by name"); a store's own game by its id there (a Steam game's appid at Steam, an Xbox game's product id at the Microsoft Store).

3 and 4 are `Lookup`, on threads of its own once the sources have been read and the first frame is out, for the games of the snapshot that lack a picture, most recently played first; what any finds goes into the cache as 2. Settings > Art's **Download art online** (`art.online`, on until turned off) turns all of them off: nothing is asked of any service, and the stores' files and the cache are all there is. A change to the order or to which sources are on starts a lookup under way again in the new order; what is already in the cache stays (Refresh all art and details fetches it all again in the new order).

### Matching by name

Every store's search gives near names too (DLC, soundtracks, editions, other games with the word in them), so a name matches only by this rule (`library::art::names`, tested on made-up names): both names written plainly (lower case; ™ ® © a space; `&` as "and"; every run of anything but letters and digits one space), then set apart from the edition, build and platform words at their end (`Deluxe Edition`, `Game of the Year Edition`, `GOTY`, Steam's `Enhanced` and `Legacy`, `PS4 & PS5`, `(PlayStation®5)`, `for Windows 10`, `(Xbox Series X|S)` and the like, from fixed lists; never `Remastered`, often a game of its own); the two must then be the same and not empty. The search sends the name, and while no answer is the game, its words alone (`Warhammer 40000 Space Marine 2`, which the PlayStation Store needs), then those without the last word (the Microsoft Store finds "Battlefield™ 6" only under "Battlefield"). Where none is the game the log says `art: steam <id>: Xbox: <n> candidates, none the same name`, never the name. `crates/library/tests/art_live.rs`, ignored by default, asks the real stores for a list of public titles and prints each candidate and why it was taken or not. Never a prefix, never "contains", never a store's first hit regardless: "Hadrel" is not "Hadrel II", "Hadrel 2" or "Hadrel: Rally". Of several that match, the very same plain name before an edition of it, then the store's own preference (PlayStation's `Full Game` before a `Bundle`, never an add-on; SteamGridDB's verified entry first), then the store's order. Only Steam items of `type: app`, Microsoft products of `Type: Game` and PlayStation links of a game category are considered.

**Why a table and not a `Source` method.** Step 3 is `library::art::store_online`, one table keyed by the source's key, not a method of `model::Source`: a source reads only its client's files and never the network (above), and every request for art, with its pace and manners, is the lookup's, in one place. What only the client's files know goes to the lookup on the game, as `Game::online` (`model::OnlineArt`): the id the store's catalogue knows the game by where it is not `source_id` (an Xbox game's `StoreId`), and the addresses of pictures the client named (the Epic launcher's). The database keeps it as `art` rows `online:<part>`.

A store's catalogue or CDN may change; one whose endpoint proves unreliable is taken out of the table, with why, here.

**The Xbox source's own square.** A package's large tile logo (the config's `Square480x480Logo`, else the manifest's `Square310x310Logo`) is the game's square from its files; its 150, 44 and store logos are icons, taken only by a game with no product in the Store (the lookup can do better for the others). A package has nothing portrait: its cover comes from the Store's `Poster`, else SteamGridDB, else its square cropped.

What the lookup asks of SteamGridDB, `https://www.steamgriddb.com/api/v2` with `Authorization: Bearer <key>`:

- The game: `/games/<platform>/<id>` where the service knows the store (`steam` for Steam's appid, `egs` for Epic's `AppName`, `gog` for GOG's product id); else, or when that is 404, `/search/autocomplete/<name>`, taking only a result whose name is the game's once case, marks (™ ® ©), punctuation and `&`/"and" are set aside, the first verified one of those. A near name is no match: no art is better than another game's.
- Its pictures: `/grids/game/<id>?dimensions=600x900` (cover), `/heroes/game/<id>` (hero), `/grids/game/<id>?dimensions=920x430,460x215` (header), `/grids/game/<id>?dimensions=1024x1024,512x512` (square), each with `types=static&nsfw=false&humor=false&epilepsy=false&mimes=image/png,image/jpeg,image/webp`, asked first with `&styles=alternate` and only when that finds nothing without a style; the first result that says none of those flags, downloaded from its own address with no key on it, kept if it is a PNG, JPEG or WebP by its bytes.
- **Plain art first.** SteamGridDB has no "official" or stock style for grids or heroes (its OpenAPI: grids `alternate`, `blurred`, `white_logo`, `material`, `no_logo`; heroes `alternate`, `blurred`, `material`; only logos and icons have `official`), and no sort. `alternate` is the plain box-art style; the others are each a made treatment, so asking for `alternate` first keeps custom banners out as far as the API allows (docs/research/art-sources.md).
- Only the kinds the sources before it in the order did not give.

**Misses.** A picture looked for and not found is remembered in the cache's folder for the game, apart for each place: `<kind>.store.none` for the game's own store online, `<kind>.steam.none`, `<kind>.xbox.none`, `<kind>.ps.none` for Steam, the Microsoft Store and the PlayStation Store (a search that found no game of the name is a miss of each kind asked), `<kind>.none` for SteamGridDB, each holding the time, and not asked for there again for seven days. So a key entered the day after asks SteamGridDB for what the store had not. Nothing found for the game at all is the same for each kind it lacked. A picture that comes later removes both. Settings > Art's **Refresh all art and details** forgets every picture and every miss and looks everything up again, at once and in the background; the Tile menu's **Refresh art** does it for one game (docs/spec/settings.md 16.8, #190).

Checked against the real service on 2026-11-16 (Portal 2 as Steam 620, Fortnite as `egs/Fortnite` and `egs/fn`, The Witcher 3 and Cyberpunk 2077 as `gog/<id>`, a name search): the reply is `{"success":true,"data":...}`, a grid's fields `id, score, style, width, height, nsfw, humor, notes, mime, language, url, thumb, lock, epilepsy, upvotes, downvotes, author`; an unknown game, or an unknown platform name, is `404 {"success":false,"errors":["Game not found"]}`; a wrong key `401 {"success":false,"errors":["Invalid API key"]}`; it sent no rate-limit headers. EA's content ids, Ubisoft's `uplay_id`s and Battle.net's product codes were not found under `origin`, `uplay` or `bnet`, so those games are found by name.

**Politeness.** Two games at a time, and at least 250 ms between any two requests to one host (each store's catalogue, SteamGridDB, and each picture host by its name). A 429 (or 503) makes every worker wait that host's `Retry-After`, or 30 s doubled each time in a row, ten minutes at most, before asking it again; a request asked to wait five times is given up for this run. SteamGridDB's 401 stops every lookup at once, says so once in a Toast, and is remembered (`art.steamgriddb_refused` in the settings table) until another key is entered. Pictures are static PNG, JPEG or WebP, by their bytes, 24 MB at most.

**Privacy.** Only a game's id at a store, or its name (with its marks taken out) to a store's search or SteamGridDB's, goes to a service, and to a picture's host nothing but the address. The key is the settings row `art.steamgriddb_key`; it goes to SteamGridDB's API alone, and is never logged, never in an error, and never shown (Settings shows dots). The log names no game by its name. Each game something was asked about online has one line, by its source and its id there: `art: steam 620: cover Steam, hero SteamGridDB, header Steam, square Xbox`, each kind asked for in that run with the source that gave it (`its store`, `Steam`, `Xbox`, `PlayStation`, `SteamGridDB`), `none` when no source had it, `failed` when a request failed. And one line a run with counts and timings: `art: 12 looked up, 9 found, 3 none, in 2.1 s; pictures: 40 store files, 12 cache, 9 store online, 3 SteamGridDB` (`, 1 failed` before the time when a request failed; "looked up" counts the games something was asked about online; "pictures" those the run's games have from each place: the stores' files on the PC, our cache from earlier runs, and in this run the stores online and SteamGridDB). And: `art: Steam asked to wait; waiting 30 s` (the host by its name: `Steam`, `the Microsoft Store`, `the PlayStation Store`, `GOG`, `SteamGridDB`, or a picture's host), `art: SteamGridDB refused the key: no more lookups until it is changed`, `art: cleared 9 pictures`, `settings: art.steamgriddb_key set` / `forgotten`, and `settings: art.online = false` / `true`.

**Chosen by the user** (#213, docs/spec/art-picker.md). The Tile menu's **Change art** lists SteamGridDB's candidates of a kind (while SteamGridDB is on among the sources; the stores' pictures are not offered there: its Automatic entry is what the lookup's order finds), a page at a time (`library::art::Picker`: the same politeness, on threads of its own, thumbnails only until one is chosen). A choice is a row of `art_choices` (source, source id, kind; `store` or `steamgriddb:<id>`), and a chosen picture's file is kept in `art-chosen/<source>/<source_id>/<kind>.<ext>` beside the cache, not in it: Refresh all art and details, a game's Refresh art and Clear downloaded art never touch either, and both are keyed by the store's id, so the choice follows the game across its launcher's updates. `Database::snapshot` puts a choice over whatever the lookup found. The stand-in (`standin serve-art`) serves each kind's candidates paged as SteamGridDB does, `--candidates` long.

A tile whose cover arrives while it is on screen fades it in over a quarter of a second, over the game's name (`Ui::art_arriving`, docs/ui.md "Art").

**Tests** never ask a real service: `library::art::fake::FakeService` answers on 127.0.0.1 from a script, and keeps what it was asked; under `/stores` (`Script::stores`) it is the stores' art online too, Steam's GetItems, CDN and store search, the Microsoft Store's catalogue, autosuggest and images, the PlayStation Store's `chihiro` search and images, and GOG's API, shaped as the real ones above; a store's search finds only the names a test gives it (`StoreScript::named`), so the VM's stand-in, which knows no names, sends every game that is not a store's own on to SteamGridDB as before. On the VM `standin serve-art --port <n> --key <key>` is that stand-in, finding a game of any name and a store's game of any id with a plain picture of each kind (`ART_COLOURS` and `STORE_ART_COLOURS` in `crates/standin`), and the Dashboard is pointed at it with `--art-service http://127.0.0.1:<n>` and `--store-art-service http://127.0.0.1:<n>/stores` (flags for tests only). Every end-to-end run gives `--store-art-service` (`Start-Dashboard`), at a port that answers nothing where the test has no stand-in, so no test asks a store's real services. `--screenshot` with `--data-dir` looks the art up before it draws (the stores' own online, and SteamGridDB where the database has a key), unless the database has art online turned off; with `--library <file>` too, the file's games go into that database first, `online` and all.
